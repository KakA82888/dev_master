## 1. 问题陈述（Problem Statement）

电商运营团队当前依赖人工从销售系统导出明细、用 Excel 透视计算核心指标，再手动撰写日报/周报/月报。

- **谁遇到**：电商运营专员（日频）、运营主管（周/月频），叠加临时查询需求。
- **频率**：日报每日、周报每周、月报每月，且多市场（43 国）查询随时发生。
- **成本（不解决的代价）**：
  1. **耗时**：单份日报手工制作 >30 分钟，重复劳动。
  2. **易错**：人工透视口径不一致。本项目数据集实测，"GMV 是否含退款红冲"这一口径就让三种算法结果相差 **168 万 GBP**（数据体检记录），证明口径不统一的现实风险。
  3. **不可审计**：数字来源于"人脑计算"，出错无法复现，复盘/监管时无法自证。
  4. **规模化瓶颈**：多市场、多周期查询时人力无法覆盖。

**证据基础**：数据集 UCI Online Retail II（2009-12 ~ 2011-12，1,067,371 行原始），经 ETL 清洗入库为 `sales_detail` 1,033,031 行，已锁定 GMV 基线 19,642,692.15 GBP。

## 2. 目标（Goals）

**用户目标**
- **G1 自然语言一键生成**：运营用日常语言（"生成昨日日报"）在 ≤2 分钟内获得结构化报表，无需懂 SQL/Excel。
- **G2 指标可信可审计**：所有数字由计算组件产出、可复现，指标准确率 ≥99%。
- **G3 人机协同闭环**：生成草稿 → 人工确认 → 归档导出，保留确认版本与审计痕迹。

**业务目标**
- **G4 提效**：单份日报生成从 >30 分钟降至 ≤2 分钟。
- **G5 口径统一**：以《指标口径与数据字典 v1.0》为唯一事实口径，全项目统一。
- **G6 可交付**：满足课程任务书六项硬指标与六类文档交付要求。

## 3. 非目标（Non-Goals）

明确本版**不做什么**，防止范围蔓延：

- **NG1 不做实时数据流接入**：数据源为静态数据集（已落库），不接实时 API/消息队列。原因：课程时间窗内外部数据源不稳定，且非核心验收项。
- **NG2 不做多数据源融合**：仅以单一事实表 `sales_detail` 为准，不引入天池/其他数据集。原因：双源会引入口径冲突与对账复杂度，核心是"自动化报表"而非"数据治理"。
- **NG3 不做预测性分析/经营建议**：Agent 负责"呈现事实指标"，不输出"建议下周怎么做"等预测。原因：避免模型臆造结论（任务书要求"禁止模型直接生成数字"），降低幻觉风险。
- **NG4 不做多租户/企业级权限体系**：不做多组织数据隔离与企业级 RBAC（行级权限、自定义角色、权限矩阵配置均不涉及）。**但按任务书 §6.2「按角色控制数据访问权限」要求，实现基础双角色**：`admin`（可查看与管理全部用户报告，`?scope=all`）与 `user`（仅本人报告），另含基础用户管理（注册/登录）。原因：角色控制为任务书明文要求，完整企业权限体系则超出课程交付范围。
- **NG5 不做移动端原生 App**：仅 Web 响应式页面。原因：验收以 Web 为主，时间窗有限。

## 4. 用户故事（User Stories）

**角色**：电商运营专员（Operator）、运营主管（Manager）、数据管理员（Admin）、系统（Agent）。

> 说明：以上为**业务视角角色**（用于描述用户故事与交互诉求）；系统实现层面按任务书 §6.2 落地为 `admin` / `user` 两个**访问控制角色**，详见《03_后端API与数据模型设计》§3「角色控制」。

### P0（核心）
- **US1（运营专员）**：作为运营专员，我希望用自然语言下指令（"生成上周德国周报"），以便无需技术背景也能产出标准报表。
- **US2（运营专员）**：作为运营专员，我希望系统自动计算 GMV/订单量/客单价/转化率/退款率及环比，以便不必手工透视。
- **US3（运营主管）**：作为运营主管，我希望在预览页查看报告草稿与异常标注，确认无误后"确认回写"，以便保留审核痕迹。
- **US4（运营专员）**：作为运营专员，我希望报告可导出 Markdown 与 Word 双格式，以便粘贴 IM 或正式归档。
- **US5（任意用户）**：作为用户，我希望登录后才能使用系统，以便报表数据不对外暴露。

### P1（重要）
- **US6（运营主管）**：作为运营主管，我希望在历史列表查看过往报告（含指令、状态、版本），以便复盘与复用。
- **US7（运营专员）**：作为运营专员，我希望系统正确解析市场/周期切换（如"英国本月月报"），以便覆盖多场景。
- **US8（数据管理员）**：作为数据管理员，我希望用户管理支持注册与登录鉴权，以便基础账号安全。

### P2（未来，架构预留）
- **US9（运营主管）**：我希望配置定时任务（每日自动生成昨日日报），以便无人值守。
- **US10（运营专员）**：我希望用 LLM 让报告结论更自然流畅，以便直接对外汇报。

## 5. 需求（Requirements · MoSCoW）

### P0 · Must-Have（无之不可交付）

**R1 自然语言指令解析**
- 描述：解析用户输入，提取 `report_type`（日报/周报/月报）、`date_range`（相对/绝对/中文区间）、`market`（Country 维度或"全部"）。
- 验收（Given/When/Then）：
  - Given 用户输入"生成上周德国周报"；When 系统解析；Then 识别 `report_type=weekly`、`market=Germany`、`date_range=上周`（相对锚点取数据最大日期 2011-12-09）。
  - 解析准确率 **≥90%**（评测集 ≥50 条，三要素全对计 1 条正确）。
- 依赖：S2 规则解析器已实现；D8 接入 LLM 双通道（`LLM_MODE=llm` 优先、失败回退规则）。

**R2 指标计算（单一事实口径）**
- 描述：基于 `sales_detail` 计算 5 指标 + 环比，全部由 `scripts/metrics/` 纯函数产出，禁止模型生成数字。
- 验收：5 指标偏差 ≤0.5%（双轨对账 pandas vs SQL 差异=0）；全量 GMV 对账 19,642,692.15 误差 <0.01 GBP。
- 引用：《01_指标口径与数据字典_v1.0》。

**R3 报告生成（Markdown + 异常标注）**
- 描述：将指标包渲染为结构化日报/周报/月报，含趋势、环比、异常标注。
- 验收：模板缺项 = 0；异常按阈值表标注（只标注、不臆测原因）。

**R4 异步生成与状态机**
- 描述：`POST /generate` 后台异步计算，状态 `pending→running→drafted`（或 `failed`）；前端轮询预览。
- 验收：单份日报端到端 **≤2min**（含计算与渲染）；状态机严格流转，非法跳转拒绝。

**R5 人工确认与回写**
- 描述：`drafted` 态可 `confirm`（`version+1`）→ `confirmed`；`confirmed` 可 `archive`。
- 验收：确认后版本自增、可审计；越权访问返回 404。

**R6 用户鉴权**
- 描述：注册/登录 JWT 鉴权，受保护接口需 Bearer token。
- 验收：未带 token 返回 401；密码 bcrypt 哈希存储（bcrypt==4.0.1 已验证兼容）。

**R7 报告导出 Word**
- 描述：`drafted`/`confirmed` 报告可导出 `.docx`（docxtpl 模板渲染，python-docx 备选）。
- 验收：Word 可正常打开无乱码；内容与预览一致。

### P1 · Should-Have（重要但非阻塞）

**R8 历史管理与检索**：`GET /reports` 列表（按用户隔离）、详情、删除。
**R9 多市场/多周期覆盖**：43 国市场映射 + 日/周/月粒度。
**R10 评测集与跑分**：≥50 条指令 golden，自动评测解析/指标。
**R11 安全自查**：提示词注入防护（用户指令不得进入系统提示执行）、越权防护、边界校验。

### P2 · Could/Won't（本版不做，架构预留）
**R12 定时任务**（APScheduler 已装，接口预留）。
**R13 LLM 增强结论**（`LLM_MODE=llm` 双通道已预留）。
**R14 多数据源接入**。

## 6. 成功指标（Success Metrics）

**硬指标（任务书验收基线）**
| 编号 | 指标 | 目标 | 测量方式 |
|---|---|---|---|
| SM1 | 指标准确率 | ≥99% | 双轨对账差异=0 + 全量金额断言；评测可复现 |

- SM6 报告复用率：历史报告被重新查看/导出比例。
- SM7 评审通过率：指导老师/答辩对交付物满意度。
