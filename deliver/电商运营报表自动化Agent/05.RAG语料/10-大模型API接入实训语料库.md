# 大模型API接入实训语料库

**主题：** 大模型 API 的申请、接入与双通道设计
**适用范围：** 后端开发、AI 应用开发、学习者
**版本：** v1.0

---

## Q: 如何申请大模型 API Key？

**A:** 以 SiliconFlow（硅基流动）为例：
1. 打开官网注册并登录账号
2. 进入控制台完成实名认证（部分平台调用前需要）
3. 在"API 密钥"页面点击新建，命名（如 `report-agent-dev`）
4. **立即复制保存**（多数平台只显示一次）

**标签：** API密钥, 申请流程, 大模型接入, 实操步骤

---

## Q: API Key 应该如何安全管理？

**A:** 四条要求：
1. 写入 `.env` 文件，并确保 `.env` 被 `.gitignore` 忽略，**不入库**
2. 不在聊天工具、截图、文档中粘贴密钥
3. 开发/测试/生产使用不同 Key，便于分别限额与吊销
4. 怀疑泄露立即到控制台删除并重建（**轮换**）

**标签：** 密钥安全, 环境变量, gitignore, 安全规范

## Q: 什么是 OpenAI 兼容接口？为什么重要？

**A:** 指接口格式与 OpenAI 官方一致（同样的 `base_url`、`/v1/chat/completions` 路径、请求响应结构）。重要性在于：切换供应商只需改三项配置（`LLM_BASE_URL`、`LLM_API_KEY`、`LLM_MODEL`），代码无需改动。本项目即通过该兼容层支持不同大模型服务。

**标签：** OpenAI兼容, 接口标准, 供应商切换, 架构设计

---

## Q: 大模型在本项目中承担什么职责？有哪些硬约束？

**A:** 只承担**意图解析（NLU）**：把自然语言指令转为结构化 JSON（报表类型、起止日期、市场）。

硬约束：
1. 绝不生成或编造任何金额、销量数字——数值一律由计算组件产出
2. 只输出纯 JSON，不含解释与代码块标记
3. 输出必须通过字段校验（报表类型白名单、日期格式）
4. 任何异常都由编排层捕获并回退规则通道

**标签：** 职责边界, 硬约束, 意图解析, 架构约束

---

## Q: 为什么采用"双通道"而不是只用大模型？

**A:** 因为大模型存在不可用风险：未配置 Key、网络异常、超时、返回格式非法。如果只有大模型通道，这些情况下系统将完全不可用。双通道设计中，规则通道（关键词 + 日期解析）作为兜底，零依赖、亚秒级响应，保证系统始终可用；大模型通道则在可用时提供更强的理解能力。

**标签：** 双通道, 失败回退, 可用性, 容错设计

---

## Q: 大模型解析失败时系统如何表现？

**A:** 编排层捕获异常后自动回退规则通道，用户仍能获得正常报表（只是解析由规则完成）。系统会在备注中记录"大模型解析失败，已回退规则通道"及原因。这样演示或答辩现场即使网络异常也不会中断。

**标签：** 失败回退, 容错, 备注记录, 可用性保障

---

## Q: 为什么说"用推理模型做意图解析"不划算？

**A:** 意图解析属于结构化抽取任务，不需要长链推理。推理型模型（如 DeepSeek-R1）单次响应可能需要 9–52 秒，成本也更高，而对结构化抽取没有额外收益。生产环境建议改用更快的对话模型（如 DeepSeek-V3），切换只需修改 `.env` 中的 `LLM_MODEL` 一行。

**标签：** 模型选型, 推理模型, 成本与延迟, 优化建议

---

## Q: 接入大模型后如何评测其效果？

**A:** 用同一评测集分别跑两条通道，对比准确率：
- 分层抽样若干条正常指令，比较规则通道与大模型通道的解析准确率
- 验证安全不变量：危险指令在大模型模式下是否仍被安全网关拦截（必须 100%）
- 做真实 HTTP 端到端验证：观察耗时是否符合预期（大模型通道明显更慢，可用于确认走了哪条通道）

**标签：** 双通道评测, 对照实验, 安全不变量, 评测方法
