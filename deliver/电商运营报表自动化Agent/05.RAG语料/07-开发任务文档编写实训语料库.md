# 开发任务文档编写实训语料库

**主题：** 用 AI 共创把需求拆解为可执行的开发任务
**适用范围：** 项目经理、技术负责人、学习者
**版本：** v1.0

---

## Q: 开发任务文档与 PRD 有什么区别？

**A:** PRD 回答"做什么、为什么做"（业务视角）；开发任务文档回答"怎么拆、谁做、做到什么程度算完成"（执行视角）。PRD 是需求基线，任务文档是把基线拆成可逐条验收的工作项，并标注依赖关系与交付物。

**标签：** 任务文档, PRD区别, 文档定位, 项目管理

---

## Q: 任务粒度如何把握？

**A:** 以"**能被独立验收**"为准。过大的任务（如"完成整个后端"）无法估算与验收；过细的任务（如"创建一个变量"）则管理成本高于收益。本项目的粒度参考：一个任务对应一个文件或一组紧密相关的文件，且有明确的验收命令与预期结果。

**标签：** 任务粒度, 独立验收, 拆分方法, 项目管理

## Q: 什么是可测试的验收标准？举例说明。

**A:** 指能用命令或观察结果客观判断的标准。示例：

| 差（不可测） | 好（可测） |
|---|---|
| 后端功能完成 | `python -m pytest app/backend -q` 全部通过 |
| 指标计算正确 | 双轨对账脚本输出差异 = 0 |
| 前端界面美观 | `npm run typecheck` 0 error；构建成功 |
| 解析准确率高 | 评测集主集 ≥90%、留出集 ≥90% |
| 安全防护到位 | 17 条危险指令 100% 被拦截 |

**标签：** 验收标准, 可测试, 客观判断, 质量门禁

## Q: 如何确定任务之间的依赖关系？

**A:** 从数据与产物的流向倒推。本项目的关键依赖链：
`口径文档 → 数据清洗 → 指标模块 → 双轨对账 → Agent 编排 → 后端接口 → 前端界面 → 导出`
其中指标内核必须先于编排，因为所有数值都来自内核；评测应尽早启动，因为硬指标（准确率）需要证据。识别关键路径后，非关键路径上的任务（文档、语料）可以并行。

**标签：** 依赖关系, 关键路径, 任务排序, 项目管理

## Q: 里程碑应该怎么设置？

**A:** 里程碑是"可演示、可验证的阶段成果"，而不是日期。本项目设置了三个：
- **M1 全链路闭环可演示**：登录 → 指令 → 计算 → 预览 → 确认 → 导出
- **M2 硬指标达标**：指标一致性 ≥99%、解析准确率 ≥90%、日报 ≤2 分钟
- **M3 交付完备**：文档、语料、PPT 齐备

每个里程碑都有明确的验证方式，避免"感觉快完成了"这类模糊判断。

**标签：** 里程碑, 可验证, 阶段成果, 进度管理

## Q: 任务文档中容易遗漏哪些任务？

**A:** 四类常被遗漏：
1. **测试任务**（单测/接口测试/端到端测试）
2. **评测任务**（评测集构建、跑分、bad case 迭代）
3. **文档任务**（各类交付文档、部署手册）
4. **安全任务**（注入防护、权限隔离、安全自查）

建议在拆解时按"开发 / 测试 / 评测 / 文档 / 安全"五类逐类检查。

**标签：** 任务遗漏, 测试任务, 文档任务, 检查清单

## Q: 风险清单怎么写才有用？

**A:** 每条风险要写清"风险 → 影响 → 应对"，且应对要可执行。示例：

| 风险 | 影响 | 应对 |
|---|---|---|
| 口径反复变更 | 数值全部返工 | 口径文档先行并确认，变更走记录 |
| 评测自验偏差 | 准确率不可信 | 建留出集 + 双通道对照 + 人工抽查 |
| 大模型超时/失效 | 演示失败 | 双通道设计，失败自动回退规则通道 |
| 文档滞后 | 交付不完整 | 每阶段结束即补文档并做缺口审计 |

**标签：** 风险管理, 应对措施, 风险清单, 项目管理

## Q: 如何用 AI 高效生成任务文档？

**A:** 让 AI 基于已有文档（PRD + 设计文档）拆任务，而不是凭空生成。提示词要点：给出技术栈、要求输出阶段划分与任务清单、每条任务包含描述/验收标准/涉及文件/依赖，并明确"任务粒度要能被独立验收"。生成后人工评审依赖关系与遗漏项。

**标签：** AI共创, 提示词, 任务拆解, 实操方法
