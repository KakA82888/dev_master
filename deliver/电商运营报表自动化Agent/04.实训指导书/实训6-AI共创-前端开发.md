# 实训6 基于AI共创的前端开发

## 一、实训目标

1. 掌握把 UI/UX 设计文档转化为 React 代码的方法（Design Tokens 先行）
2. 学会实现报表类界面的关键交互：指令输入、生成轮询、报告预览、确认归档、导出下载
3. 理解前端状态与后端状态机的对齐（按钮可用性守卫）
4. 能够通过 AI 实现组件化渲染（Markdown 块 → 组件）与异常高亮
5. 掌握前端构建与后端静态托管的联调方式

## 二、实训内容

### 1. 背景知识

- **Design Tokens 落地**：把设计文档中的颜色、字号、间距、圆角写成 CSS 变量，全站复用。
- **轮询（Polling）**：报告生成是长任务，前端提交后按固定间隔查询状态，直到 drafted 或 failed。
- **组件化渲染**：把报告 Markdown 解析为块（标题/引用/表格/列表），再映射为 React 组件，便于对异常行做特殊样式。
- **状态守卫对齐**：前端按钮的可用性必须与后端一致（仅 drafted 可确认、pending 不可导出）。
- **单端口部署**：`vite build` 产物由后端静态托管，避免生产环境跨域与端口配置问题。

### 2. 项目结构

```
01.code/app/frontend/
├── src/
│   ├── tokens.css        设计系统变量
│   ├── styles.css        组件与页面样式
│   ├── api.ts            接口封装（含 token 存取、错误语义化、导出下载）
│   ├── markdown.ts       轻量 markdown 块解析
│   ├── ui.tsx            Toast / StatusBadge / Modal / EmptyState / Skeleton
│   ├── report.tsx        报告预览与操作条
│   ├── pages.tsx         登录页 / 工作台 / 历史页
│   ├── main.tsx          入口与 hash 路由
│   └── types.ts          类型与状态中文标签
├── vite.config.ts        dev :5173，/api 代理到 8000
└── package.json
```

## 三、实训步骤

### 步骤1：与AI共创搭建前端骨架与设计系统

**操作：**
打开与 AI 对话窗口，输入以下内容：

```bash
请按 UI/UX 设计文档实现 React 前端（React 18 + TypeScript + Vite），要求：
1. 先落地 tokens.css（主色/语义色/中性灰阶/字号/8pt 间距/圆角/阴影/状态徽章色）
2. 通用组件：Toast、StatusBadge（六态）、Modal、EmptyState、Skeleton、Spinner
3. 三个页面：登录/注册页、工作台页、历史报告页
4. 不要引入第三方 UI 组件库，全部基于自建设计系统实现
```

**操作结果：**
- AI 生成 `tokens.css` / `styles.css` / `ui.tsx` 等基础文件。

> 【截图位】建议插入：AI 生成前端代码截图（images5/前端代码.png）

**操作验证：**
- 运行 `npm run typecheck` → 0 error；
- 运行 `npm run dev` → 页面可访问，样式正常。

**操作说明：**

1. **为什么先做 Design Tokens？**
   先定义变量再写组件，能避免"每个页面各写一套颜色/间距"，后续改版只需改一处。

2. **为什么不用第三方组件库？**
   报表界面以表格与状态展示为主，自建组件更可控、体积更小，也便于与设计文档一一对应。

### 步骤2：与AI共创实现核心交互

**操作：**

在 AI 对话窗口输入：

```bash
请实现工作台的核心交互：
1. 指令输入框 + 快捷指令 chips（昨日日报/上周周报/上月月报等）
2. 提交后轮询报告状态（1.5s 间隔），展示 pending → running → drafted 的进度
3. 报告预览：把 markdown 块渲染为组件，异常指标行用琥珀色警示
4. 操作条：确认（仅 drafted 可点）/ 归档 / 导出下拉（Markdown、Word）/ 删除（二次确认）
5. 导出下载需解析响应头中的中文文件名
6. 历史页：按类型、市场、状态、关键字四维筛选
```

**操作结果：**
- AI 生成 `report.tsx` / `pages.tsx` / `api.ts` / `markdown.ts`。

> 【截图位】建议插入：前端功能模块实现截图（images5/逐一实现前端功能模块.png）

> 【截图位】建议插入：面诊分析界面（此处为本项目工作台界面）截图（images5/工作台界面.png）

**操作验证：**
- 走通"输入指令 → 生成 → 预览 → 确认 → 导出"全流程；
- 检查按钮可用性是否与状态一致；
- 检查异常指标是否高亮。

> 【截图位】建议插入：报告生成界面截图（images5/报告生成界面.png）

**操作说明：**

1. **为什么要轮询而不是长连接？**
   实现简单、兼容性好，且报表生成时长可控（秒级到数十秒），轮询足够。

2. **中文文件名下载的坑**
   需从 `Content-Disposition` 响应头解析文件名，并对编码做兼容处理，否则中文名会乱码。

3. **前端状态守卫**
   即使后端有校验，前端也应同步禁用按钮，避免用户点了才报错，体验差。

### 步骤3：构建与联调

**操作：**

```bash
cd app/frontend
npm run build          # 产出 dist
# 后端启动后会自动托管 dist，访问 http://127.0.0.1:8000 即完整应用
```

**操作验证：**
- 构建成功且无类型错误；
- 通过 8000 端口访问，前端资源正常加载、接口调用正常。

> 【截图位】建议插入：启动前端服务截图（images5/启动前端服务.png）

**操作说明：**

1. **开发模式 vs 生产模式**
   开发时前端 5173 + 代理到 8000（热更新）；生产时构建产物由后端托管（单端口）。

2. **构建产物不入库**
   `dist/` 属于构建产物，一般不纳入版本管理，但交付包中需内置（见 `部署版code`）。

## 四、注意事项

1. **AI工具使用**：把设计文档与接口文档一并提供给 AI，生成代码才能与后端对齐。

2. **类型检查**：每次改动后运行 `npm run typecheck`，避免类型错误累积。

3. **无障碍与响应式**：数字等宽对齐、按钮有焦点态、窄屏下表格可横向滚动。

4. **错误提示**：接口错误要给出可读提示；被安全网关拦截时应显示"安全拦截 + 原因"，而非笼统的"生成失败"。

5. **实训管理**：前端改动后需重新构建，否则页面不会更新（后端托管的是构建产物）。
